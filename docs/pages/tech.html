01

Password security — salt + pepper

We never store the actual password. We store a one-way hash made with argon2id — a deliberately slow, memory-hungry recipe. Three layers stack up:

Hash = the scrambled output; you cannot reverse it back to the password. Salt = a random value added per user, so two people with the same password get totally different hashes (argon2 does this automatically). Pepper = one secret key we keep outside the database and mix into every password. It's the layer most apps skip.

Scenario · the database gets stolen

An attacker walks off with the whole users table — every hash and every salt. Without the pepper (which lives in our secrets manager, not the database), they still can't crack even weak passwords: every guess has to be re-peppered, and they don't have the pepper. Salt makes each hash unique; pepper makes a stolen database useless.

02

Login & sessions — two keys, instant revoke

Once you log in we hand your browser two tokens. A short-lived access token (≈15 min) that proves who you are on every request, and a long-lived refresh token that quietly gets you a new access token when it expires — so you're not logged out every 15 minutes. We also keep a session record in Redis, which is the kill switch.

Scenario · you hit "log out everywhere" or get banned

A plain token can't be un-issued — it's valid until it expires. That's why we also check Redis on every request: deleting the session there means the very next request is rejected, instantly, even though the token still looks valid. Tokens for speed, Redis for control.

03

No double-booking — the database referees

Two guests can tap "Book" on the same car for the same dates at the exact same millisecond. Only one can win. We don't trust our own code to check "is it free?" then "mark it taken" — between those two steps, the other guest sneaks in. Instead the database itself enforces a unique rule: one row per car per day. The first write wins; the second is physically rejected.

Scenario · 20 people book at once (we tested this)

We fired 20 simultaneous bookings at one car. Exactly one succeeded; the other 19 got a clean "Not available" — no half-bookings, no overselling. The loser's partial data is rolled back automatically. The guarantee lives in the database, so no amount of traffic can break it.

04

Payments & webhooks — never lose a charge

Stripe takes the card, then tells us "this succeeded" with a webhook — a POST to our server. Two dangers: someone could fake that message, and Stripe sends it more than once. So we verify a signature (proves it's really Stripe), and record each event's id so we only ever act on it once. If our handler trips, the event is parked and retried instead of vanishing.

Scenario · the charge went through but our server hiccupped

Before, if our code threw an error right after the card was charged, the event was gone — money taken, no booking. Now the event is parked and replayed until it lands. And the flip side: even if Stripe sends the same "paid" ten times, the booking is only ever marked paid once — no double charges, no lost charges.

05

Admin isolation — a locked, hidden building

The admin panel is a separate app (its own port, 3005), reachable only at a secret address — every other path returns "not found," so search engines and attackers can't even discover the login. On top of that, every admin action re-checks with the database that you're really an admin — the app never trusts a role claimed by the browser.

Scenario · a normal user tries to become admin

Even if someone edits their browser to claim "role: admin," it changes nothing — the server asks the database on every request, and the database says "guest." The only admin is the one provisioned from a secret env file; there is no button, API, or request anywhere that can promote an account. Hidden door, real lock, guard checks ID every time.
